# AICam ESP32

The ESP32-S3 runs CircuitPython, joins Wi-Fi, and exposes HTTP interfaces for
manual and [H618](../aicam_h618/README.md) lane control. This module follows the
device filesystem layout without an `app/var` split.

## Firmware baseline

[firmware.toml](firmware.toml) records the restoration baseline:

| Setting | Value |
| --- | --- |
| Board ID | `espressif_esp32s3_devkitc_1_n8r8` |
| CircuitPython | `10.2.1` |
| Firmware build date | `2026-05-13` |

Restore matching board firmware and compatible `.mpy` libraries. Git stores
the version record and required `lib/` files, not the firmware image.

The checked-in libraries come from the official 10.x bundle dated 20261010;
its URL and SHA-256 are recorded in `firmware.toml`. CircuitPython 10.2.1
expects bytecode format 6. Format 5 libraries from older bundles cause
`ValueError: incompatible .mpy file`. When updating libraries, replace the
deployed copies with the matching checked-in files and remove obsolete files;
the old `lib/asyncio/manifest.mpy` is not part of this bundle.

## File roles

| Path | Purpose |
| --- | --- |
| `boot.py` | Disables USB storage for the current wireless workflow |
| `code.py` | Starts `robot_lane_tracking.robot_app.run()` |
| `robot_lane_tracking/` | Wi-Fi server, HTTP routes, and motor control |
| `lib/` | CircuitPython application libraries |
| `lib_cp8/` | Inactive backup of libraries from the earlier CP 8 setup |
| `settings.example.toml` | Wi-Fi and web workflow configuration template |
| `settings.toml` (ignored) | Actual device settings and credentials |
| `test/` | Earlier experiments and hardware checks |

`boot_out.txt` is generated by CircuitPython and ignored. Use the firmware
record to identify the expected baseline.

## Restore and deploy

1. Install firmware matching `firmware.toml` if the device needs restoring.
2. Copy `settings.example.toml` to `settings.toml` locally and set the Wi-Fi SSID,
   password, web API password, and hostname.
3. Provision Wi-Fi/web workflow through the available initial connection before
   relying on wireless file updates.
4. Upload `lib/`, `robot_lane_tracking/`, `code.py`, `boot.py`, and the actual
   `settings.toml` to the CircuitPython root with the wireless development tool.
5. Reload the application, inspect the console, and verify connectivity.

`README.md`, `firmware.toml`, and `settings.example.toml` are documentation and
templates, not startup dependencies. Deploy `test/` and `sd/` when needed.
Preserve device settings and generated metadata with tools that delete
destination-only files. The current `boot.py` disables USB storage, so restore
Wi-Fi configuration and access before relying on wireless-only updates.

### Previous library backup

`lib_cp8/` preserves the previous library files, including the old
`asyncio/manifest.mpy`. The archived `boot_out_2.txt` records CircuitPython 8.2.9
dated 2023-12-06; the exact original library bundle date is unknown. The directory
name identifies the historical setup, not a verified bundle version. This
directory may be uploaded alongside `lib/` to keep a device-local
backup, but it is not on CircuitPython's default library search path. Do not
add it to `sys.path` or import from it.

The backup is not compatible with the current CircuitPython 10 firmware. To
roll back, stop the application, preserve the current `lib/`, restore a complete
old library set into `/lib/` without mixing versions, and use matching firmware.
Keep a copy on the Mac or in Git as well: a device-only backup can be lost when
the filesystem is reformatted during firmware recovery.

## HTTP interface

`robot_app.py` starts the server and motor loop:

| Route | Purpose |
| --- | --- |
| `/` | Browser keyboard control page |
| `/cmd?m=LEFT` | Manual action; also accepts `RIGHT`, `STRAIGHT`, and `STOP` |
| `/lane?m=LEFT` | Lane decision from H618 |
| `/estop` | Emergency stop |
| `/arm` | Re-arm the motor controller |

The application prints a URL with port 5000, but `sta_server.py` calls
`server.start(bind_ip)` without specifying a port. Verify the actual listening
port before configuring the H618 `--motor-url` or laptop recorder URL.

## Development checks

### Wheel wiring check

`test/test_wheel_control.py` is an interactive hardware check, not an automated
unit test. Lift all wheels off the ground and keep the motor power disconnect
accessible. Stop the running application with Ctrl+C in the wireless serial
console, then run from the REPL:

```python
exec(open("test/test_wheel_control.py").read())
```

Confirm the initial stopped state, type `run` before each short pulse, and
answer `yes` only if the expected wheel(s) and direction were observed and all
wheels stopped afterward. Any other response ends the test. It covers each
wheel forward/backward, both wheels forward/backward, and both pivot directions.
The test uses the new vehicle reference: BIN1/BIN2 (IO4/IO5) is left and
AIN1/AIN2 (IO6/IO7) is right when facing forward. Backward is the opposite
direction; pivot directions are viewed from above. The left-wheel check showed
BIN positive throttle moves backward, so left forward now uses negative throttle.
The right-wheel check showed AIN negative throttle moves backward, so right
forward now uses positive throttle. All eight checks were confirmed on hardware
on 2026-10-13. These test-only definitions do not change the existing application
mapping in `motor_control.py`.

Default throttle is 0.14 for 0.75 seconds. If it is too low to move an unloaded
wheel, execute the script with automatic execution disabled and call `run`
explicitly; limits are 0.30 throttle and 2 seconds:

```python
scope = {"__name__": "wheel_check"}
exec(open("test/test_wheel_control.py").read(), scope)
scope["run"](throttle=0.20, duration=0.75)
```

The script defines its own wheel mapping and direction signs and does not
import the application controller, start the server or load saved speed
settings. It resets all PWM outputs after each pulse and on normal exit,
exceptions, or Ctrl+C, then releases
the pins. A reset failure, firmware crash or lost console cannot guarantee an
immediate stop; disconnect motor power if anything behaves unexpectedly. Do not
run the older full-throttle tests for this check. The application's existing
wheel reference has not yet been aligned with this test; check its mapping
before driving on the ground. This check does not validate lane decisions or
networking.

The current `code.py` runs this interactive test instead of starting the robot
server. To restore the application entry point after aligning its wheel mapping,
replace the test call with `from robot_lane_tracking.robot_app import run` and
`run()`.

Edit locally, upload runtime changes, and inspect the device console. Check
Wi-Fi, the browser page, and motor wiring/control before testing lane commands.
Motor pins and tuning are in `robot_lane_tracking/motor_control.py`.

Commit code, libraries, and configuration examples. Actual credentials stay in
the ignored `settings.toml`; fill those in again after a fresh clone.
