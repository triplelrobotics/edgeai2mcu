# AICam ESP32

The ESP32-S3 runs CircuitPython, joins Wi-Fi, and exposes HTTP interfaces for
manual and [H618](../aicam_h618/README.md) lane control. This module follows the
device filesystem layout without an `app/var` split.

## Firmware baseline

[firmware.toml](firmware.toml) records the restoration baseline:

| Setting | Value |
| --- | --- |
| Board ID | `espressif_esp32s3_devkitc_1_n8r8` |
| CircuitPython | `10.2.1` |
| Firmware build date | `2026-05-13` |

Restore matching board firmware and compatible `.mpy` libraries. Git stores
the version record and required `lib/` files, not the firmware image.

The checked-in libraries come from the official 10.x bundle dated 20261010;
its URL and SHA-256 are recorded in `firmware.toml`. CircuitPython 10.2.1
expects bytecode format 6. Format 5 libraries from older bundles cause
`ValueError: incompatible .mpy file`. When updating libraries, replace the
deployed copies with the matching checked-in files and remove obsolete files;
the old `lib/asyncio/manifest.mpy` is not part of this bundle.

The previous CircuitPython 8 library backup was removed after hardware
verification of the current libraries. Historical copies remain in Git history.

## File roles

| Path | Purpose |
| --- | --- |
| `boot.py` | Disables USB storage for the current wireless workflow |
| `code.py` | Runs the interactive application motor check (temporary entry point) |
| `robot_lane_tracking/` | Wi-Fi server, HTTP routes, and motor control |
| `lib/` | CircuitPython application libraries |
| `settings.example.toml` | Wi-Fi and web workflow configuration template |
| `settings.toml` (ignored) | Actual device settings and credentials |
| `test/` | Earlier experiments and hardware checks |

`boot_out.txt` is generated by CircuitPython and ignored. Use the firmware
record to identify the expected baseline.

## Restore and deploy

1. Install firmware matching `firmware.toml` if the device needs restoring.
2. Copy `settings.example.toml` to `settings.toml` locally and set the Wi-Fi SSID,
   password, web API password, and hostname.
3. Provision Wi-Fi/web workflow through the available initial connection before
   relying on wireless file updates.
4. Upload `lib/`, `robot_lane_tracking/`, `code.py`, `boot.py`, and the actual
   `settings.toml` to the CircuitPython root with the wireless development tool.
5. Reload the application, inspect the console, and verify connectivity.

`README.md`, `firmware.toml`, and `settings.example.toml` are documentation and
templates, not startup dependencies. Deploy `test/` and `sd/` when needed.
Preserve device settings and generated metadata with tools that delete
destination-only files. The current `boot.py` disables USB storage, so restore
Wi-Fi configuration and access before relying on wireless-only updates.

## HTTP interface

`robot_app.py` starts the server and motor loop:

| Route | Purpose |
| --- | --- |
| `/` | Browser keyboard control page |
| `/cmd?m=LEFT` | Manual action; also accepts `RIGHT`, `STRAIGHT`, and `STOP` |
| `/lane?m=LEFT` | Lane decision from H618 |
| `/estop` | Emergency stop |
| `/arm` | Re-arm the motor controller |

The checked-in HTTPServer 4.8.2 library defaults to port 5000, so
`server.start(bind_ip)` serves the application there. Configure the H618
`--motor-url` or laptop recorder URL with the board's current IP and port 5000.

For a device REPL, run a chosen script with
`exec(open("test/FILE_NAME.py").read())`. Stop the current program first and
soft reload between scripts that allocate pins. This executes top-level code
immediately; the historical GPIO/PWM scripts do not have ready confirmations.
Prefer the two verified checks below for today's motor hardware.

The historical HTTP scripts only define functions when loaded. To deliberately
start the print-only server, for example:

```python
scope = {"__name__": "http_check"}
exec(open("test/test_legacy_http_print_go_stop.py").read(), scope)
scope["run_server"]()
```

Both HTTP experiments need `adafruit_httpserver` and `asyncio`; the motor
version also needs `adafruit_motor`. With the checked-in HTTPServer 4.8.2,
`server.start()` defaults to port 5000, matching the H618 go/stop clients.
Starting a demo AP changes network behavior and may interrupt wireless access.

`test_legacy_small_demos.py` imports all dependencies eagerly, including `neopixel`,
`adafruit_httpserver` with `Websocket`, and `adafruit_motor`, even for UART/LED
methods. IO1 LED needs an external circuit; the RGB demo uses IO48; UART needs
external wiring at 9600 baud (TX/RX or IO17/18). The AP pages request the renamed
JS/CSS assets at the HTTP document root, while the repository stores them in
`test/`: copy the two assets to the device HTTP root or adapt document root/URLs
before trying the browser demos. Their motor logic uses the old wheel reference
and has no disconnect timeout; review it before reuse.

Renaming local files does not remove old copies on the device. When deploying
this cleanup, update any personal launch snippets and remove obsolete device
copies deliberately; no device files were changed by this local cleanup.

### Wheel wiring check

`test/test_wheel_control.py` is an interactive hardware check, not an automated
unit test. Lift all wheels off the ground and keep the motor power disconnect
accessible. Stop the running application with Ctrl+C in the wireless serial
console, then run from the REPL:

```python
exec(open("test/test_wheel_control.py").read())
```

Confirm the initial stopped state, type `run` before each short pulse, and
answer `yes` only if the expected wheel(s) and direction were observed and all
wheels stopped afterward. Any other response ends the test. It covers each
wheel forward/backward, both wheels forward/backward, and both pivot directions.
The test uses the new vehicle reference: BIN1/BIN2 (IO4/IO5) is left and
AIN1/AIN2 (IO6/IO7) is right when facing forward. Backward is the opposite
direction; pivot directions are viewed from above. The left-wheel check showed
BIN positive throttle moves backward, so left forward now uses negative throttle.
The right-wheel check showed AIN negative throttle moves backward, so right
forward now uses positive throttle. All eight checks were confirmed on hardware
on 2026-10-13. This script defines its own mapping independently of
`motor_control.py`.

Default throttle is 0.14 for 0.75 seconds. If it is too low to move an unloaded
wheel, execute the script with automatic execution disabled and call `run`
explicitly; limits are 0.30 throttle and 2 seconds:

```python
scope = {"__name__": "wheel_check"}
exec(open("test/test_wheel_control.py").read(), scope)
scope["run"](throttle=0.20, duration=0.75)
```

The script defines its own wheel mapping and direction signs and does not
import the application controller, start the server or load saved speed
settings. It resets all PWM outputs after each pulse and on normal exit,
exceptions, or Ctrl+C, then releases
the pins. A reset failure, firmware crash or lost console cannot guarantee an
immediate stop; disconnect motor power if anything behaves unexpectedly. Do not
run the older full-throttle tests for this check. To check the application
controller itself, use the application motor controller check below. This
wiring check does not validate lane decisions or networking.

### Application motor controller check

The application now uses the verified physical wheel reference: left is BIN
(IO4/IO5, forward sign -1), right is AIN (IO6/IO7, forward sign +1). Its object
names and speed pairs have been aligned without changing the per-pin throttle
outputs or their update order for existing commands.

The current `code.py` runs `test/test_motor_controller.py`, which imports the
actual application `MotorController`. Upload these three files to the matching
device paths, then soft reload with the wireless serial console open:

- `robot_lane_tracking/motor_control.py`
- `test/test_motor_controller.py`
- `code.py`

Keep all wheels lifted and motor power disconnect accessible. Enter `ready`,
then confirm the initial stopped state with `yes`. Enter `run` for each step:
STOP, STRAIGHT, LEFT, RIGHT. Each step lasts 0.75 seconds and stops before asking
for `yes` to confirm the observation. For LEFT, both wheels move forward with
the physical left wheel slower; for RIGHT, the physical right wheel is slower.
STRAIGHT requests the same throttle on both wheels; actual wheel speeds can
differ mechanically. Answer anything other than `yes` if a result is incorrect
or unclear. During a pulse, `q` or Ctrl+C ends the test and attempts to stop both
motors; disconnect motor power if stopping fails.

The test overrides loaded speed settings with base 0.14, turn delta 0.06, and
minimum effective throttle 0.08, without saving them. It does not start the HTTP
server or validate model predictions. Soft reload before repeating the test;
the controller retains its allocated PWM pins until reload. The separate wheel
wiring check above remains available and does not import the controller.

On 2026-10-15, the user confirmed all four application motor checks passed on
hardware through the wireless serial console after the mapping refactor.

After hardware validation, restore the normal application entry point by
